# Cross-repository write access for the local web manifest

Question: how can `pitaka-web` Actions commit the web selection in the private `itsdevjimbo/pitaka-deploy` repository after publication or promotion? This note informs [the Wayfinder decision](https://github.com/itsdevjimbo/pitaka-web/issues/299); it does not choose or provision a credential.

## Current trigger boundary

`Publish Build` runs on a completed `CI` `workflow_run`, checks that the upstream run was a successful `main` push for the exact SHA and attempt, then builds and uploads a 14-day artifact. `Promote Production Build` runs on a `v*` tag push and invokes the release promotion script. Both currently use `pitaka-web`'s `GITHUB_TOKEN`; promotion also reads `RELEASE_IMMUTABILITY_TOKEN`. See [Publish Build](../../.github/workflows/publish-build.yml), [Promote Production Build](../../.github/workflows/promote-production-build.yml), and [ADR 0018](../adr/0018-retain-promoted-web-builds-for-rollback.md).

GitHub says a workflow's `GITHUB_TOKEN` is limited to the repository containing that workflow. Increasing its `contents` permission does not grant write access to `pitaka-deploy`; a GitHub App token or personal access token is needed for cross-repository API access. [GitHub authentication guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github), [GITHUB_TOKEN guidance](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token).

## Viable credentials

| Credential | Minimum target access for `versions/local.json` | Operational constraint |
| --- | --- | --- |
| GitHub App installation token | Install the app on `pitaka-deploy` with repository **Contents: read and write**; mint a token limited to that repository and permission. The REST contents update and HTTPS Git push both accept installation tokens with Contents access. | Store the app ID and private key as web workflow secrets. Mint the installation token late; it expires after one hour. App identity is independent of a human account. [Installation token endpoint](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app), [Git access permission](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app), [workflow App authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow). |
| Fine-grained personal access token | Select only `pitaka-deploy` under its resource owner and grant repository **Contents: read and write**. The REST contents endpoint accepts this token. | Store as a web Actions secret; access follows the token owner's rights and token expiry. Organization ownership may require token approval. [Token configuration](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), [contents endpoint](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents). |
| Write-enabled SSH deploy key | Grant a deploy key write access to `pitaka-deploy`; use it for an SSH Git fetch/commit/push. | The key is repository-specific and long-lived; store the private key as a web Actions secret. This is a Git transport option, not a REST bearer token. [Deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys). |

`Contents: write` is repository-wide permission, not a path-scoped grant to `versions/local.json`. No **Workflows** permission is needed for this path; GitHub calls for it when editing `.github/workflows`. Branch protection or rulesets on `pitaka-deploy/main` may still reject direct writes, regardless of token contents permission, so the chosen actor must be allowed by its actual rules. [Contents endpoint permissions](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents), [GitHub App Git permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app), [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

## Write method and concurrency

The REST Contents API can read the current file, then `PUT /repos/itsdevjimbo/pitaka-deploy/contents/versions/local.json` with Base64 content, a commit message, `branch: main`, and the current blob `sha` (required for an update). This makes a single-file commit. A concurrent edit can invalidate that SHA; re-read and reapply the web-only transform against the latest file before retrying. Git over HTTPS with an App/PAT or SSH with a deploy key can instead fetch `main`, change the file, commit, and push; a concurrent push similarly requires fetching and replaying the intended web-only change. These concurrency implications are inferences from the API's required current SHA and Git's ref update behavior. [Contents API](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents), [GitHub App HTTPS Git authentication](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app).

## Event and secret constraints

GitHub explicitly permits a `workflow_run` workflow to access secrets and write tokens even if its upstream workflow could not. That is a privileged boundary: GitHub warns against running untrusted code, using untrusted caches, or letting upstream artifacts control privileged operations. Here the publish job checks out and builds the upstream SHA; any new deploy credential should be acquired only after artifact validation and kept out of build steps and their environment. This placement is a security inference from the documented boundary and the current workflow sequence. [GitHub `workflow_run` event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run), [secure use reference](https://docs.github.com/en/actions/reference/security/secure-use).

A tag push is a normal `push` trigger. Repository Actions secrets can be referenced in such a workflow. GitHub withholds Actions secrets for fork-triggered workflows and Dependabot-triggered events; those restrictions should be considered if the trigger or actor changes. `Promote Production Build` already references a repository secret, but availability of any new credential depends on configuring it in the web repository or an accessible organization secret. [Push event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push), [using secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets), [Dependabot restrictions](https://docs.github.com/en/code-security/reference/supply-chain-security/troubleshoot-dependabot/dependabot-on-actions).

## Decision left open

Choose the actor and transport after checking `pitaka-deploy/main` branch rules and whether an App or PAT is already available. The GitHub App gives a short-lived, repository-scoped automation identity; the fine-grained PAT is simpler to establish; the deploy key supports SSH Git only. All three can implement the agreed direct commit if the branch rules permit the actor. The implementation should define retries and idempotence for concurrent publish and promotion writes.
